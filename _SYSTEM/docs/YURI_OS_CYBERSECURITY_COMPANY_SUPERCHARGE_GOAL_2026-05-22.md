## Failsafe Verification Contract

No output from either main unit is trusted on authority alone.

- Opus checks itself before handing work back: changed files, assumptions, tests, protected-surface safety, and known weak spots.
- Codex independently re-reads changed files, verifies diffs, runs tests or explains blocked tests, and rejects unproven claims.
- Codex work gets the same treatment: local changes must be checked against tests, release gates, and the plan before being treated as complete.
- For security/offensive work, the rail is strict: owned systems, explicit authorization, isolated labs, defensive deliverables, and no uncontrolled target guidance.
- Any contradiction between Opus and Codex becomes a written decision record or test, not a vibe.

## Strategic Position

YURI should not become a narrow "AI-agent scanner" company. That is the beachhead. The larger company thesis is:

> YURI is an AI-native cyber operating system for seeing, testing, hardening, and governing the new attack surfaces created by agents, automation, memory, model routing, tool access, browser control, cloud/SaaS connectors, and cross-region AI adoption.

The first buyer-ready proof must still be smaller and sharper:

> YURI can assess and harden AI-agent, skill-chain, MCP, browser, memory/RAG, and model-route security with source-backed findings and controlled lab evidence.

## Research Expansion Requirements

The cyber program must not collapse into western-only or agent-only research. It must track:

- Machine-speed cybercrime: ransomware, infostealers, BEC, fraud, crypto theft, DDoS, access brokers.
- Identity and SaaS: session theft, OAuth abuse, API keys, SaaS connectors, over-permissioned service accounts.
- Cloud and supply chain: CI/CD, packages, GitHub Actions, model artifacts, dependency trust.
- AI-native attack surfaces: prompt injection, indirect prompt injection, tool poisoning, MCP compromise, RAG/memory poisoning, browser-agent abuse, code-agent sabotage, eval regression.
- OT/ICS and sector risks: manufacturing, healthcare, energy, telecom, finance, legal, startups/SMBs, high-net-worth private users.
- Regional pressure:
  - Europe/DACH/Switzerland: ENISA, NIS2, DORA, GDPR/revFADP, EU AI Act, SME/MSP security.
  - West: CISA/NIST/FBI, hyperscaler AI, cyber insurance, identity/cloud incident economics.
  - Asia: Singapore AI Verify, Japan industrial cybersecurity, Korea zero-trust/AI-security, China TC260-style GenAI security requirements, India/CERT-In, Taiwan/SEA supply-chain exposure, and regional model ecosystems.

## Company-Scale Capability Ladders

### 1. Intelligence

Build a living cyber intelligence map, not static notes. Every threat maps to source evidence, region, customer pain, YURI capability, missing proof, lab scenario, scanner rule, guardrail, and report section.

### 2. Assessment

Turn YURI's internal guardrails into external assessment workflows:

- AI-agent and tool-use assessment.
- Skill/rule/plugin/MCP scanner.
- Repo and supply-chain scanner.
- Model-route trust posture inventory.
- Memory/RAG poisoning assessment.

### 3. Lab Validation

Create owned, local, explicitly safe labs that prove capability:

- Vulnerable web/API lab.
- Cloud/IAM misconfiguration lab.
- MCP/tool poisoning lab.
- RAG/memory poisoning lab.
- Browser-agent compromise lab.
- Phishing/deepfake awareness simulation.
- Malware/infostealer behavior lab in isolated sandboxes.
- DDoS/load testing only against local owned services.
- OT/ICS only with toy/CTF systems.

### 4. Guardrails

Convert lab failures into deterministic rails:

- input rails;
- retrieval rails;
- dialog rails;
- execution rails;
- output rails;
- tool-input and tool-output rails;
- health rails;
- model-route rails;
- memory/RAG provenance rails.

### 5. Runtime Monitoring

YURI eventually needs action lineage, health truth, stale-state detection, agent event schemas, and repair flows. Do not claim SOC/MDR maturity until telemetry and real client operations exist.

### 6. Client Reporting

Reports must split executive and technical views:

- executive: risk, business impact, next decision;
- technical: evidence, reproduction scope, remediation, tests;
- legal boundary: not legal advice, no compliance guarantee unless explicitly scoped by a qualified provider.

### 7. Managed Operations Later

Managed security operations are a later company capability. Do not claim SOC/SIEM/XDR/MDR now. Build toward it through evidence, telemetry, and partner pilots.

## Cyber Lab Harness Roadmap

The lab is the proof engine. Every offensive or adversarial capability must remain owned, local, synthetic, CTF-style, or explicitly authorized. The goal is defensive truth, not uncontrolled exploitation.

Minimum lab scenarios:

- Prompt-injection replay over direct, indirect, nested, and tool-output injection.
- Malicious MCP server with deceptive tool schemas and hostile responses.
- Browser-agent lab with fake SaaS portals, fake secrets, malicious pages, and form exfiltration.
- Memory poisoning lab with gradual drift, acute policy injection, and rollback testing.
- RAG poisoning lab with source trust tiers and retrieval conflict tests.
- CI/CD supply-chain lab with malicious workflows and package scripts.
- Vulnerable web/API lab for authz, SSRF, injection, path traversal, and secret leakage.
- Local load-test lab to verify fail-closed behavior under pressure.
