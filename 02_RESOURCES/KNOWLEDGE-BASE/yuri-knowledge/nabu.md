### HOUSE 2: GOVERNANCE
**Location:** `/NABU/02_GOVERNANCE/`  
**Purpose:** How work gets routed, validated, and escalated.

**Core Documents:**

1. **routing.md** — Agent assignment logic
   - When does Sonnet get a task? (speed-critical, well-defined scope)
   - When does Opus get a task? (ambiguous, high-stakes, novel domain)
   - When does a subagent spawn? (parallel work, isolation needed)
   - When does human override occur? (confidence threshold exceeded)
   - Escalation tree (who decides what?)

2. **quality-gates.md** — Validation checkpoints
   - Type checking (TypeScript strict mode, no `any`)
   - Linting (code style, naming consistency)
   - Testing (unit, integration, E2E; coverage thresholds)
   - Security (SAST scans, dependency audit, secrets detection)
   - Manual review (human checkpoint gates)
   - **Gate behavior:** Hard failure (no merge until fixed). No warnings. No overrides.

3. **conflict-resolution.md** — When agents disagree
   - Agent A says "use pattern X"; Agent B says "use pattern Y"
   - Resolution: Compare against CLAUDE.md; if none, human decides
   - Escalation: Document conflict in governance log; add precedent to future decisions
   - Example: Opus recommends comprehensive testing; Sonnet says "iterate fast"
     → Governance rule: security/financial work requires Opus + full test suite; prototypes use Sonnet + rapid iteration

4. **audit-trail.md** — Provenance tracking
   - Every major decision: who decided, when, why, alternatives considered
   - Every blueprint invocation: cost, outcome, lessons
   - Every escalation: what was escalated, why, resolution
   - Monthly audit: governance effectiveness review

**Integration with YURI Modes:**
- Mode 1 (Direct Execution): Simplified governance; minimal validation
- Mode 2 (Parallel Intelligence): Multiple agents; strong conflict resolution needed
- Mode 3 (Recursive Research): Deep documentation of decision tree
- Mode 4 (Self-Evolution): Governance rules themselves are learned and updated
- Mode 5 (Delegation): Orchestrator uses full governance framework
- Mode 6 (Long-Form Assembly): Multi-phase governance; dependencies tracked
- Mode 7 (Meta-Analysis): System diagnostics; governance stress-tested

**Location:** `/NABU/03_MEMORY/`  
**Purpose:** How knowledge persists, evolves, and doesn't contradict itself.

**Core Documents:**

   - **Layer 1: CLAUDE.md** (always loaded, highest priority)
     - Routing logic, workflow definitions, quality standards, non-negotiable rules
   - **Layer 2: Auto Memory (MEMORY.md)** (session-learned patterns, top 200 lines loaded)
     - Skill candidates, debugging insights, architecture decisions
   - **Layer 3: Rules Directory** (path-targeted rules, activate on demand)
     - Project-specific conventions, client preferences, domain rules
   - **Precedence:** CLAUDE.md > Auto Memory > Rules Directory > Session

   - Observation: NOESIS watches blueprint executions
   - Extraction: When pattern repeats 2x, flag as learnable
   - Codification: Write to Auto Memory; test on execution 3
   - Promotion: After 3 successful executions, promote to CLAUDE.md rule
   - Deprecation: When conditions change, mark rule as aging; eventually archive

3. **version-control.md** — Tracking rule evolution
   - Each rule has: created date, last modified, confidence score, usage count
   - Archive old rules (conditions changed, better pattern found)
   - Keep change log (why was this rule modified?)
   - Rollback procedure (revert to known-good rule if new version breaks)

4. **conflict-detection.md** — When memory contradicts itself
   - Example: CLAUDE.md says "Always use Opus for security work"
       but recent Auto Memory says "Sonnet + tight gates works just as well"
   - Detection: Automated scan for contradictions between layers
   - Resolution: Force explicit decision (keep old rule? upgrade to new? hybrid?)
   - Example output: "Rule 'use-opus-security' conflicts with learned pattern 'sonnet-gates-work'. Decision: Keep both; clarify conditions in CLAUDE.md."

### HOUSE 5: RESILIENCE
**Location:** `/NABU/05_RESILIENCE/`  
**Purpose:** Survival when systems fail.

**Core Documents:**

1. **failure-detection.md** — How to know something broke
   - Agent produces no output: check execution logs, API errors
   - Agent produces wrong output: compare against success criteria
   - Agent drifts from constraints: behavior outside guardrails
   - Cost unexpectedly high: token overage, repeated work
   - Learning is being undone: recent patterns contradict older knowledge
   
   **Detection signals:**
   ```
   Type             Signal                           Check
   Silent failure   No output for 60 minutes         Cron logs; API status
   Semantic error   Output passes gates but is wrong Quality evaluator rubric
   Constraint drift Agent writes outside assigned files File system audit
   Cost explosion   Monthly spend 2x+ baseline      Token usage tracking
   Memory conflict  Rules contradict each other      Conflict detection scan
   ```

2. **fallback-procedures.md** — What to do when blueprint fails
   - Blueprint: GAN Loop (adversarial evaluation)
     Fallback: Use simpler single-pass validation until loop debugged
   - Blueprint: Autonomous Swarm
     Fallback: Route to single orchestrator (slower, more reliable)
   - Blueprint: Self-Evolving Hooks
     Fallback: Pause learning; revert to last known-good CLAUDE.md

3. **rollback.md** — Undoing corrupted state
   - Process: (1) Detect corruption, (2) Identify last-good state, (3) Restore, (4) Verify
   - Backup strategy: Git history (code changes), Auto Memory history (learned rules)
   - Time to rollback: <5 minutes (documented procedure, practiced regularly)
   - Data loss: Minimize via continuous versioning (every rule update is versioned)

4. **canary-testing.md** — Safe deployment of new rules
   - New rule: test on 5% of work first
   - Monitor: does success rate stay the same? Cost per execution?
   - Graduated rollout: 5% → 25% → 100% over 3 days
   - Abort threshold: if success rate drops >10%, rollback immediately

5. **disaster-recovery.md** — Multi-region failover (future)
   - Currently: single region (Claude APIs only)
   - Prepare: documented procedure to switch to backup model provider
   - Objective: 30min downtime maximum
