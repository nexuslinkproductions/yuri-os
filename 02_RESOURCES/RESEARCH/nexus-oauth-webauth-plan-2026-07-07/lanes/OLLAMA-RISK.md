Here is the ranked security risk table. Each risk is grounded in the existing YURI research (NEXUS-SECURITY-AUDIT-2026-07-02, nexus-social-connect-deep-research-2026-07-05) and standard OAuth/SaaS threat models.

| Risk | Severity | Why | Mitigation |
|---|---|---|---|
| **SHARED-CLI-CREDENTIAL hazard** — operator's personal Anthropic/Cursor OAuth tokens embedded in in-app chat, served to all tenants | **CRITICAL** | One leaked token = every tenant can call Anthropic/Cursor APIs as the operator. ToS violation (resale of personal subscription). No tenant isolation — the agent has the operator's full credential, not a scoped sub-token. Blast radius: all tenants, all conversations, API cost burn on operator's billing. | Never embed the operator's personal tokens. Run a per-tenant, server-side, rate-limited, tool-scoped agent proxy that holds its own credentials (or no credentials and uses the app's own API key). The agent must be tenant-isolated at the model-call boundary, not sharing a single auth session. |
| **Multi-tenant data isolation / RLS bypass** — tenant A reads or modifies tenant B's connector tokens, leads, or chat history | **CRITICAL** | Postgres RLS is the only isolation layer. If `SET LOCAL app.workspace_id` is missing, or a query uses `service_role` bypass, or a public route lacks `SECURITY DEFINER`, every tenant sees every other tenant's data. IDOR is the default failure mode. | Every query scoped by `workspace_id` via RLS policy + `SET LOCAL` middleware on every request. Public routes use `SECURITY DEFINER` functions with explicit tenant param. Negative tests (tenant A ≠ tenant B) in CI. Never trust client-supplied `workspace_id`. |
| **Refresh-token rotation failure & reuse detection** — stolen refresh token grants permanent access | **CRITICAL** | If the app does not rotate refresh tokens on each use (burn old, issue new), a leaked refresh token is a permanent backdoor. Without reuse detection, the same token can be used from two locations simultaneously — the attacker and the legitimate user both work. | Implement refresh-token rotation per RFC 6749 §10.4: issue a new refresh token on every refresh, revoke the old one. Log and alert on reuse (stolen-token indicator). Store only the current valid hash; the old one is dead on first use by either party. |
| **Authorization-code interception (no PKCE)** — attacker on the same device/network steals the auth code via intercepted callback | **CRITICAL** | Without PKCE (RFC 7636), the authorization code is a bearer credential. Any process on the same machine, or a man-in-the-middle on the redirect, can exchange it for tokens. OAuth 2.1 makes PKCE mandatory. | Enforce S256 PKCE on every OAuth flow. The `code_verifier` is generated client-side, hashed to `code_challenge`, sent in the authorize request, and the raw verifier is sent in the token exchange. The server must reject requests without a valid `code_verifier`. |
| **OAuth redirect-URI manipulation / open-redirect** — attacker registers a lookalike URI and intercepts the auth code | **HIGH** | If the app accepts wildcard or prefix-match redirect URIs (e.g., `https://*.ngrok.io/callback`), an attacker can register a subdomain they control and receive the auth code. Open redirects on the app's own domain compound this — attacker crafts a link that passes the redirect check but bounces the code to an attacker site. | Register exact, per-provider redirect URIs — no wildcards, no prefix matching. Validate the full URI including path, not just the origin. Close any open redirect on the app domain. Use a server-side allowlist, not client-side validation. |
| **Token storage at rest — plaintext in Postgres** — database breach leaks all provider access/refresh tokens | **HIGH** | Connector tokens (Google, Meta, Instagram, Threads) stored server-side in Postgres. If the column is not encrypted at the application layer, a SQL injection, backup leak, or DBA compromise exposes every user's delegated access to their social accounts. | Encrypt tokens at rest using AEAD (AES-256-GCM) with a key stored outside the database (vault/KMS/env). Decrypt only in the application server at request time. Never log or serialize decrypted tokens. Column-level encryption, not just TDE. |
| **Missing state/CSRF on OAuth callback** — attacker binds their social account to the victim's session | **HIGH** | Without a cryptographically random `state` parameter validated on the callback, an attacker can initiate an OAuth flow, intercept the victim's session, and link the attacker's provider account to the victim's app account. This grants the attacker access to the victim's app data via the connector. | Generate a `state` parameter (crypto-random, session-bound, 5-min TTL) on every OAuth start. Validate it exactly on the callback — reject if missing, mismatched, or expired. Store the expected state server-side, not in a client cookie. |
| **Provider app-review / permission over-scoping** — app requests more scopes than needed, blocking or delaying provider approval | **HIGH** | Google/Meta/Instagram require app review for sensitive scopes (e.g., `youtube.upload`, `instagram_basic`). Requesting all scopes upfront (as the current MS connector does) triggers review for every scope, even unused ones. In Testing mode, refresh tokens expire in 7 days — the app breaks for any user beyond the test account. | Request incremental, minimal scopes per connector. Separate "Testing" (owner-only, 7-day tokens) from "In Production" (reviewed, stable tokens). Move to published status before onboarding real users. Document which scopes need review per provider. |
| **Session/cookie security misconfiguration** — session token leaked via XSS, CSRF, or network intercept | **HIGH** | If session cookies lack `HttpOnly`, `Secure`, and `SameSite=Lax` (or `Strict`), an XSS vulnerability leaks the session token, or a CSRF attack performs actions as the authenticated user. On non-HTTPS connections (demo mode), the cookie is sent in plaintext. | Set `HttpOnly` (prevents JS access), `Secure` (HTTPS-only), `SameSite=Lax` (CSRF protection). Use short-lived session JWTs (15-30 min) with refresh tokens. Never bind to `0.0.0.0` in production. Enforce TLS on all cookie-bearing endpoints. |
| **Authorization-code in URL logs / referer header** — code leaks to third-party analytics or server logs | **MEDIUM** | The OAuth callback URL contains the authorization code as a query parameter. If the app logs the full URL, or the browser sends a `Referer` header to a third-party resource (analytics, CDN, images), the code leaks. An attacker with log access or network position can exchange it. | Switch to POST-based callback (form POST body, not query string) where the provider supports it. Strip query params from logs. Set `Referrer-Policy: no-referrer` on the callback page. Use PKCE (already critical) so a leaked code alone is insufficient without the `code_verifier`. |
| **DPoP not implemented** — bearer access tokens can be replayed by any party that intercepts them | **MEDIUM** | Without DPoP (RFC 9449), an access token is a pure bearer credential. Any process, proxy, or log that sees the token can reuse it until expiry. For a multi-tenant SaaS with server-side token storage, a compromised server process leaks all active tokens. | Bind access tokens to the client's ephemeral keypair via DPoP. The server verifies the DPoP proof on every request. Token replay requires the private key, which never leaves the client. This is the single highest-leverage control for the token-broker architecture. |
| **Connector token leakage via agent tool calls** — the in-app chat agent can read or use connector tokens meant for a different tenant | **MEDIUM** | If the agent has access to the token store (even indirectly via tool calls), a prompt-injected agent could exfiltrate tokens or use them to call provider APIs as a different user. The agent is a new attack surface on the token vault. | The agent must never receive raw tokens. Mint short-lived (5-15 min), scope-narrowed, DPoP-bound access tokens on demand. The agent proves possession of its own keypair per request. The token vault is a write-only oracle to the agent — it cannot list or export tokens. |
| **Supabase GoTrue anon key exposure** — public anon key used as a de facto auth bypass | **MEDIUM** | GoTrue's `anon` key is public by design (sent to the client), but if RLS policies rely on it as the sole gate, an attacker can call any "public" endpoint with the anon key and enumerate users, read public data, or trigger unauthenticated flows. | Use the anon key only for client-initiated auth flows (sign-up, sign-in). All data-access endpoints must enforce RLS with the user's JWT, not the anon key. The `service_role` key is server-side only — never in the client. |
| **OAuth token refresh race condition** — two concurrent refreshes produce two valid refresh tokens | **MEDIUM** | If the app does not serialize refresh-token rotation, two concurrent requests can both succeed, producing two valid refresh-token families. An attacker who observes one can use the second family. | Serialize refresh operations per user-provider pair (database row lock or atomic compare-and-swap). The first refresh burns the old token; the second finds it already rotated and fails. Log the race as a potential token-theft indicator. |
| **Provider token scope creep** — a connector's scopes expand over time without user re-consent | **MEDIUM** | If the app adds scopes to an existing OAuth client, the user's existing token may not cover the new scopes. The app either fails silently (partial functionality) or requests re-auth without explaining why. Users may approve without understanding the new scope. | Version the scope set per connector. On scope change, force re-authorization with a clear explanation of what changed. Never silently use an under-scoped token. Store the granted scope set alongside the token and check it before each API call. |

**Summary of critical path:** The SHARED-CLI-CREDENTIAL hazard is the highest-severity item because it is a design choice, not a configuration bug — it creates a single point of compromise for the entire tenant base with the operator's personal billing attached. The three OAuth-critical controls (PKCE, refresh rotation, redirect-URI exact-match) are well-understood and must be non-negotiable gates. RLS isolation is the entire multi-tenant security model and must be verified with negative tests before any tenant data is loaded.
