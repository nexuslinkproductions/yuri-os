## 1. Blind-Check Corrections to the Gemini Plan

Use the Gemini plan as a structural inspiration, not as factual truth.

### 1.1 Remove unsupported factual claims
Do not include or depend on unverified claims about:
- Exact Claude release dates.
- Exact model pricing.
- Exact future model capabilities.
- Gartner-style forecasts.
- Specific cloud quota numbers.
- Named incidents or exploit stories unless a verified source is present in the repo or docs.
- Any dependency such as KendoReact unless it already exists in the project.

In code, the repository is the source of truth.  
In architecture, use capability-based language instead of vendor-factual language.

Bad:
```text
Claude 4.6 was released in February 2026 and has X pricing.
```

Good:
```text
Use the target reasoning model as the planner. Do not hardcode model-specific claims into product copy or code.
```

### 1.2 MCP and agent hardening must be practical
If MCP exists in the repository, treat it as a tool transport layer, not a security boundary.

Never rely on MCP roots alone for access control.  
Enforce access with actual backend permissions, sandboxing, allowlists, path normalization, schema validation, timeouts, and audit logs.

### 1.3 Background execution must be implemented only where the stack supports it
The Ctrl+B/background-task concept is valid as a UX and developer workflow reference.  
Do not implement fake backgrounding.

If the app already has a job queue, worker system, server actions, cron worker, edge worker, task table, or event bus, use that.  
If not, add the smallest robust backend task abstraction:
- `BackgroundJob`
- `BackgroundJobLog`
- `BackgroundJobStatus`
- `BackgroundJobResult`
- `BackgroundJobError`
- cancellation support
- timeout support
- retry policy
- progress events

Do not block the UI while long-running jobs execute.

### 1.4 Security language must become code constraints
The final implementation must include:
- RBAC or permission checks where user/session scope exists.
- Input validation at API boundaries.
- Output validation before writing model-generated data.
- No arbitrary shell execution from user input.
- No direct execution of model-generated commands without explicit allowlisting.
- Rate limits for expensive endpoints.
- Timeouts for all background jobs.
- Audit logs for destructive actions.
- Feature flags for experimental systems.

### 4.2 Completion service

Implement a central completion service instead of scattering completion logic across components.

Required behavior:
- When a checkbox is ticked, recalculate the parent project completion.
- `progressPercent = checkedBoxes / totalBoxes * 100`.
- If a project has zero checkboxes, it cannot auto-complete from checkbox state.
- When all checkboxes are checked:
  - mark project as `completed`;
  - set `completedAt`;
  - create one notification;
  - emit one activity event.
- The notification must be idempotent.
- If a checkbox is unticked after completion:
  - either reopen the project or mark it as active, depending on existing product logic;
  - document the chosen behavior;
  - update progress truthfully.

Pseudo-contract:

```ts
async function updateProjectCheckbox(input: {
  checkboxId: string;
  checked: boolean;
  actorId?: string;
}): Promise<{
  checkbox: ProjectCheckbox;
  project: Project;
  notificationCreated: boolean;
}> {
  validateInput(input);
  updateCheckbox();
  const stats = await countProjectCheckboxes(projectId);

  const progressPercent =
    stats.total === 0 ? 0 : Math.round((stats.checked / stats.total) * 100);

  const shouldComplete = stats.total > 0 && stats.checked === stats.total;

  updateProject({
    progressPercent,
    status: shouldComplete ? "completed" : "active",
    completedAt: shouldComplete ? now : nullIfReopened,
  });

  createNotificationOnce({
    dedupeKey: `project_completed:${projectId}`,
  });

  emitActivityEvent();

  return result;
}
```

### 4.3 Metric calculation service

Create a shared `metricService` or equivalent.

Every visible dashboard number must expose:
- value
- unit
- calculation source
- last calculated timestamp
- confidence state
- fallback copy when missing

Example:
```ts
type MetricResult<T> = {

  unit?: string;
  source: "computed" | "manual" | "external" | "derived";
  confidence: "high" | "medium" | "low" | "missing";
  calculatedAt?: Date;
  explanation?: string;
};
```

The UI should be able to show:

- can be dragged;
- participates in collision;
- has gravitational pull toward the center or cluster anchors;
- is color-coded;

### Color coding
Use existing design tokens if available.

```ts
statusColor = {
  open: "blue",
  in_progress: "violet",
  blocked: "red",
  review: "amber",
  done: "green",
  archived: "neutral",
};

priorityRing = {
  low: 1,
  medium: 2,
  high: 3,
  critical: 4,
};
```

### Physics implementation rules
First inspect dependencies.

Preferred order:
1. Existing physics or force-layout library.
2. Existing animation library plus lightweight custom physics.
3. Add a small physics library only if justified.

Must support:
- `requestAnimationFrame` loop.
- collision radius per orb.
- central attraction.
- drag pinning.
- velocity damping.
- viewport bounds.
- pause on tab hidden.
- reduced-motion mode.
- no memory leaks.
- no hydration mismatch if SSR exists.

Pseudo-physics:

```ts
for each frame:
  for each orb:
    applyCenterGravity(orb)
    applyVelocityDamping(orb)
    applyPointerDrag(orb)

  resolvePairwiseCollisions(orbs)
  resolveBounds(orbs)
  renderPositions()
```

For many tickets, avoid O(n²) collision if count is high.

## 9. Security Requirements

### 9.1 General
- No arbitrary command execution from user input.
- No model output directly executed as code.
- No unsanitized HTML rendering.
- No unsafe file path joins.
- No client-only authority for completion or status changes.
- No leaked private data on public landing routes.
- No hidden recording.
- No silent external sync.

### 9.2 Permission gates
If auth exists:
- users can only mutate scoped entities;
- admin-only sync/config endpoints are protected;
- destructive actions require explicit UI action;
- background jobs are bound to the requesting user or system actor.

### 9.3 Background jobs
Every background job must have:
- status
- owner/scope
- timeout
- cancellation
- retry limit
- error state
- logs or progress
- cleanup behavior

### 9.4 LLM-generated analysis
If any LLM-generated summaries/actions exist:
- label them as generated analysis;
- validate before persistence;
- never treat them as authoritative without review;
- keep source references where possible.

## 14. Anti-Mistake Clause

If you are unsure:
- inspect more code;
- search references;
- follow existing patterns;
- implement the smallest safe version;
- leave explicit notes;
- do not invent.

If two modules overlap:
- preserve the stronger existing behavior;
- remove duplication only after confirming references;
- avoid breaking routes.

If real data is unavailable:
- create the data contract;
- show honest empty states;
- do not generate fake certainty.

If a requested visual effect conflicts with performance/accessibility:
- implement a reduced-motion-safe version;
- provide a fallback;
- keep the feature usable.

The final result should feel more alive, more coherent, and more powerful, but the backend must become stricter, not looser.
