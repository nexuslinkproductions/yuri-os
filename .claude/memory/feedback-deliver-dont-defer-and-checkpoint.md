RULE: Two execution-discipline lessons. (a) DELIVER, don't defer-loop: when a task's scope grows mid-stream, name the expanded scope + a concrete phased delivery plan UP FRONT and ship a tangible increment each turn — do not greenlight-then-defer the same deliverable repeatedly (it reads as stalling even when each individual defer is justified). (b) CHECKPOINT long sessions: proactively offer to jump to a fresh session when context gets very deep, rather than risking tail-of-session quality on a proud/high-stakes artifact.
WHEN: long multi-task sessions; a "quick" task that balloons; deep-context tails; high-stakes/proud artifacts (Marcel's research paper, published work).
DO: surface scope growth + sequencing early and commit to a path; produce a real increment per turn (not planning-only); flag when context depth threatens quality and suggest a clean handoff (write a resume memory + a paste-ready next-session prompt).
DONT: re-defer the same build 3+ times; push quality-critical work at exhausted context; mistake thorough planning for progress.
WHY: Marcel noticed both — the repeated dashboard defers, and that a session this long risks quality at the tail. He values shipped progress and protecting the quality of work he's proud of.
