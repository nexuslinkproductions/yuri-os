RULE: Before (and while) building any non-trivial YURI mechanism, study how the field / competition / adjacent engineering disciplines solved the same problem, then transfer the excellence patterns at the MECHANISM level. Never copy code or IP. The bar is YURI code of pure excellence, not merely functional.

WHEN: any non-trivial YURI build, harden, or refactor — especially moat mechanisms (energy gate, memory, governance, cognition).

DO: local-first (`ai search` + the committed competitive docs in `02_RESOURCES/RESEARCH/`) → targeted online (raw source, bounded per research_pipeline.md) → extract excellence patterns + the hardening/failure-modes they already handle → FOLD into the design BEFORE committing code → capture genuinely-useful synthesized findings to `02_RESOURCES/RESEARCH/<topic>-<date>.md` + `ai reindex`. Cross-domain counts: e.g. resilience circuit-breakers (Hystrix/resilience4j) → governance gate hardening.

DONT: copy code or IP (mechanism-transfer only, legally clean — diamond-design discipline). Don't build from first principles alone when the field has solved adjacent hardening. Don't let the study balloon past the build — study FEEDS the build, never replaces it (no greenlight-then-defer).

WHY: the moat must be genuinely best-in-class for MUSUBI ONE to ship credible; competitors + adjacent disciplines have already paid for the hardening lessons; mechanism-transfer is YURI's innovation engine. Marcel directive 2026-06-03: "the best way we can improve, harden and overall supercharge this development is by looking at how the competition did so... not copy... study them so yuri's code is of pure excellence."
